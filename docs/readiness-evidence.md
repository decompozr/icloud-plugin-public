# Connection readiness evidence

The owner-only administration response includes process-local observations keyed by owner, account, client and service. These are evidence of a past authenticated request or completed read, not a declaration that a named host currently possesses a working connection. Registration names are not trusted host identity.

Bearer introspection supplies the client identifier, account binding, owner, granted scopes and expiry. Verifiers without this identity produce no evidence. The MCP host observes authorization after verification; discovery does not count as a provider read. Only successful mail_list_mailboxes, mail_search, mail_read, calendar_list_calendars, calendar_query_events and calendar_get_event can record a read. Errors, unsupported/incomplete results, missing events, writes and scope challenges cannot. Calendar UI completion requires both listing and an event query/read. Request arguments and provider content are never retained.

Observations contain timestamps and tool names only alongside account/client/service identifiers. They are bounded to 256 entries in memory, expire no later than the observed access token or 24 hours, and clear on restart. The protected administration response checks a nonsecret OAuth metadata fingerprint, current allowed scopes, credential generation and policy-update epoch before exposing observations. Revoked/deleted/changed grants, client settings, session expiry, credential rotation/removal and capability updates invalidate evidence. In-flight operations must finish under the same fingerprint. Changes after a browser response require refreshing diagnostics; labels deliberately say "observed at", not "currently authorized". The browser suppresses expired observations on its next periodic render.

The fingerprint reads only allowlisted metadata columns, never token/client-secret/credential values. There is no evidence table migration, grant update, new permission, automatic consent or provider probe. New evidence arrives only from existing legitimate authenticated requests. Owner-authenticated GET is the sole UI retrieval path; selections in the UI never establish an account/client relationship or widen access.

Verification uses synthetic SQLite metadata, actual MCP transport fixtures, existing owner introspection tests, desktop/mobile rendering and keyboard/error/retry checks. It does not establish live ChatGPT Calendar acceptance. After a separately authorized deployment, explicit host consent and an actual connected calendar list plus bounded event read are still required; retain and recheck Mail access.
